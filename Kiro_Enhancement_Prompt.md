## Context and Baseline

The current SPY/SPX Predictor is a daily batch pipeline that engineers a 37+ feature vector and trains a single XGBoost multi-class classifier (`multi:softprob`, 3-class: UP / NEUTRAL / DOWN) on a rolling 252-day window. The model outputs a 5-level directional prediction with a raw `softprob` confidence score. The pipeline runs once daily at 4:30 PM ET on a DGX Spark (NVIDIA GB10 GPU). Sentiment is generated by passing up to 50 news articles through DeepSeek R1 70B via Ollama. Data is stored in SQLite 3.45 with WAL mode across 11 tables.

All enhancements below must preserve the existing fallback logic (Polygon → yfinance, LLM → neutral score), the 13-step pipeline structure, and the existing dashboard layout unless explicitly stated otherwise. No enhancement should cause the pipeline to abort on step failure.

## Enhancement 1 — Regime-Adaptive Neutral Threshold

**Priority:** P1 | **File:** `trainer.py` | **Complexity:** Low

**Specification.** The current neutral zone threshold of ±0.3% is static and produces inconsistent class label quality across volatility regimes. In a low-VIX environment (VIX ≈ 12), ±0.3% is a large move and should be classified as directional; in a high-VIX environment (VIX ≈ 35), ±0.3% is trivial noise and should be classified as neutral. Replace the fixed constant with the following adaptive formula in `trainer.py`'s `get_target()` function:

```python
def get_adaptive_neutral_threshold(vix_level: float) -> float:
    VIX_BASELINE = 18.0   # long-run VIX average
    BASE_THRESHOLD = 0.003
    adaptive = BASE_THRESHOLD * (vix_level / VIX_BASELINE)
    return max(0.001, min(0.008, adaptive))  # clamp to [0.1%, 0.8%]
```

**Acceptance criteria.** When VIX = 12 the threshold evaluates to ≈ 0.002; when VIX = 18 it evaluates to 0.003; when VIX = 35 it evaluates to ≈ 0.0058. The threshold value must be logged and stored in the `predictions` table alongside each prediction.

## Enhancement 2 — Post-Hoc Probability Calibration

**Priority:** P1 | **File:** `trainer.py` | **Complexity:** Low

**Specification.** XGBoost `softprob` outputs are known to be poorly calibrated — the stated 70% confidence does not reliably correspond to 70% empirical accuracy. After the model is trained on the rolling 252-day window, fit an isotonic regression calibrator on a separate 42-day (2-month) hold-out calibration set that is excluded from training. Use `sklearn.calibration.CalibratedClassifierCV` with `method='isotonic'` and `cv='prefit'`. All downstream confidence scores must come from the calibrated wrapper, not the raw XGBoost output. The calibration set must be refreshed monthly (i.e., always the most recent 42 trading days prior to the training window).

```python
from sklearn.calibration import CalibratedClassifierCV

calibrated_model = CalibratedClassifierCV(
    xgb_model,
    method='isotonic',
    cv='prefit'
)
calibrated_model.fit(X_calibration, y_calibration)
```

**Acceptance criteria.** The Brier score of the calibrated model must be lower than the Brier score of the uncalibrated model on the calibration set. The Brier score must be stored in the `model_registry` table (see Enhancement 15).

## Enhancement 4 — Feature Drift Monitoring

**Priority:** P1 | **New file:** `drift_monitor.py` | **Complexity:** Low-Medium

**Specification.** Create a new module `drift_monitor.py` that implements Population Stability Index (PSI) and Kolmogorov-Smirnov (KS) tests for all features in the SPY predictor's feature vector. The baseline distribution for each feature is computed from the training window at the time of model training and stored as a JSON snapshot. At each daily pipeline run, the monitor compares the current day's feature values against the stored baseline.

PSI is computed using 10 equal-frequency bins. A PSI value above 0.1 triggers a WARNING status; above 0.2 triggers a DRIFT status. When DRIFT is detected in any feature ranked in the top-10 by XGBoost feature importance, the system must: (a) trigger an immediate retraining using a 63-day window instead of 252 days, (b) apply a drift penalty to the confidence score (multiply by 0.85), and (c) send a Telegram and email alert with the drifting feature names and their PSI values.

The drift status for each feature must be stored in a new `feature_drift` table with columns: `date`, `feature_name`, `psi_score`, `ks_statistic`, `ks_pvalue`, `status`.

**Acceptance criteria.** The `feature_drift` table is populated after every pipeline run. Alerts fire correctly when PSI > 0.2 for a top-10 feature. The drift penalty is applied and the penalised confidence score is displayed on the dashboard with a visible "DRIFT DETECTED" badge.

## Enhancement 9 — FinBERT Fast-Path Sentiment

**Priority:** P1 | **File:** `analyzer.py` | **Complexity:** Low-Medium

**Specification.** Implement a two-tier sentiment pipeline in `analyzer.py`. The fast path runs all articles through FinBERT (`ProsusAI/finbert` from HuggingFace `transformers`) on the existing GPU. FinBERT must complete processing of all 50 articles in under 60 seconds. The deep path runs the top 5 articles (ranked by FinBERT confidence magnitude) plus any FOMC statements or earnings call transcripts through the existing DeepSeek R1 70B model. The final aggregate sentiment score must be a weighted combination: FinBERT base score (weight 0.4) plus DeepSeek deep score for top articles (weight 0.6). If the deep path has not completed by the time the pipeline reaches Step 12 (prediction generation), the FinBERT-only score is used with a "FAST SENTIMENT" flag stored in the `daily_sentiment` table.

```python
# Install: pip install transformers torch

finbert = hf_pipeline('sentiment-analysis', model='ProsusAI/finbert', device=0)
```

**Acceptance criteria.** The FinBERT fast path completes in under 60 seconds on the DGX Spark. The `daily_sentiment` table gains a new column `sentiment_source` (values: `finbert_only`, `hybrid`). The pipeline never blocks on the deep path.

## Enhancement 10 — Model Performance Gating

**Priority:** P1 | **File:** `trainer.py` | **Complexity:** Low

**Specification.** After training a new model and before deploying it as the active model, evaluate it against the prior day's model on the most recent 21-day validation set. Reject the new model and continue using the prior model if either of the following conditions is true: (a) the new model's directional accuracy on the validation set is below 0.52, or (b) the new model's accuracy is more than 2 percentage points lower than the prior model's accuracy on the same validation set. When a model is rejected, send a Telegram and email alert with the rejection reason and both accuracy values. Log the rejection to a new `model_gate_log` table with columns: `date`, `new_model_accuracy`, `prior_model_accuracy`, `rejection_reason`.

**Acceptance criteria.** The gate fires correctly in a unit test where a deliberately degraded model is passed. The prior model remains active when the gate rejects a new model. The alert is received within 60 seconds of rejection.

**Acceptance criteria.** The stacking ensemble trains end-to-end within 15 minutes on the DGX Spark. The BiLSTM and LightGBM models are saved alongside the XGBoost model in the `models/` directory. The meta-learner's validation accuracy is stored in the `model_registry` table.

## Implementation Constraints

The following constraints apply to all enhancements:

**Backward compatibility.** No enhancement may remove or rename an existing database column, API endpoint, or configuration key without providing a migration path. All new database columns must have sensible default values to avoid breaking existing queries.

**Fallback behaviour.** Every new data fetch or computation must have a fallback to NaN or a neutral value. The pipeline must never abort due to a failure in any single enhancement.

**Performance budget.** The total daily pipeline runtime (Steps 1–13) must not exceed 120 minutes on the DGX Spark after all P1 and P2 enhancements are implemented. The FinBERT fast path (Enhancement 9) is specifically required to reduce the sentiment bottleneck.

**Testing.** Each enhancement must include a unit test in the `tests/` directory that validates the core logic with synthetic data. Integration tests are required for all new database tables and API endpoints.

**Configuration.** All new thresholds, API keys, and tunable parameters must be stored in `config.json` with documented defaults. No hardcoded secrets.
